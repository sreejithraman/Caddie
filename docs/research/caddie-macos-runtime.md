# Caddie Mac App runtime, file access, and distribution

Research date: 2026-08-01

## Question

Which macOS tools and limits apply to a menu bar app that watches user-selected local Skill Sources, starts at login, invokes the Caddie Tool, writes beneath the existing Caddie roots, and posts notifications?

## Answer for the first release

Build one native menu bar app that targets macOS 13 or later. Keep it running in the logged-in user's session and register that same app with `SMAppService.mainApp`. Do not add a launch agent, daemon, or second state store.

Do not turn on App Sandbox for the first personal-use release. The Mac App Store requires App Sandbox, but direct notarized distribution does not. This lets the app use the existing User Caddie State Root, Canonical Skills Directory, registered local Skill Sources, and installed Caddie Tool under the user's normal file rights. A sandboxed version would need user-selected read/write access and saved security-scoped bookmarks for every external root. More importantly, Apple says user-selected file access does not let a sandboxed app run programs outside its app bundle, container, or app group. Caddie's current Tool runs from the installed Caddie Skill through Node, so sandboxing would also force a new bundled Tool and runtime plan. ([App Sandbox](https://developer.apple.com/documentation/security/app-sandbox), [Preparing your app for distribution](https://developer.apple.com/documentation/xcode/preparing-your-app-for-distribution), [Accessing files from the macOS App Sandbox](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox), [Caddie Tool entry point](../../skills/caddie/tool/caddie.mjs))

Use File System Events as a change hint, not as authority for Caddie state. Watch each registered local Skill Source directory, group quick bursts, and then ask the Caddie Tool to inspect the source. Run a full inspection at app launch before starting streams from “now”; this covers changes made while the app was not running without storing event IDs. Apple can group events, and it can report dropped events or a changed watch root. On `MustScanSubDirs`, dropped-event, or root-change flags, discard any fine-grained guess and inspect the whole affected source. File-level events exist, but Apple warns that they produce far more events; Caddie does not need them when inspection already computes fingerprints. ([File System Events](https://developer.apple.com/documentation/coreservices/file_system_events), [`FSEventStreamCreate`](https://developer.apple.com/documentation/coreservices/1443980-fseventstreamcreate), [file-level event flag](https://developer.apple.com/documentation/coreservices/kfseventstreamcreateflagfileevents), [`MustScanSubDirs`](https://developer.apple.com/documentation/coreservices/1455361-fseventstreameventflags/kfseventstreameventflagmustscansubdirs), [dropped events](https://developer.apple.com/documentation/coreservices/kfseventstreameventflaguserdropped), [changed watch root](https://developer.apple.com/documentation/coreservices/kfseventstreameventflagrootchanged))

Invoke the Caddie Tool as a child process with Foundation `Process`. Pass the versioned request on standard input, read the JSON response from standard output, save standard error for diagnostics, and keep the work off the main UI thread. Set an exact executable URL and arguments instead of relying on a shell. The app still needs a product decision about how it finds a compatible Node executable and the installed Tool; this research does not choose that App–Tool interface. Foundation exposes the executable, arguments, environment, working directory, and standard streams needed for this call. ([`Process.executableURL`](https://developer.apple.com/documentation/foundation/process/executableurl), [current Caddie protocol](../../README.md#caddie-tool))

## File access and privacy

An unsandboxed app still runs under the current user's POSIX rights, access control lists, System Integrity Protection, and macOS privacy controls. Since macOS 10.15, macOS asks for consent when an app first reaches protected places such as Desktop, Documents, Downloads, iCloud Drive, network volumes, and removable volumes. The user can later revoke that access in Privacy & Security. Full Disk Access requires a manual System Settings grant and is not needed for ordinary registered Skill Sources or `~/.agents`; Caddie should report a blocked source instead of asking for broad disk access. ([Controlling app access to files in macOS](https://support.apple.com/guide/security/secddd1d86a6/web), [Files & Folders settings](https://support.apple.com/guide/mac-help/mchld5a35146/mac), [Full Disk Access](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox#Request-full-disk-access-to-use-all-files-on-a-Mac))

Let the user choose each new local Skill Source with `NSOpenPanel`, then persist the source through Caddie's existing state. For the unsandboxed first release, the app does not need security-scoped bookmarks. If a later sandboxed build appears, the open panel extends access to the chosen directory and its children, and the app must save an explicit security-scoped bookmark, resolve stale bookmarks, call `startAccessingSecurityScopedResource()`, and balance it with `stopAccessingSecurityScopedResource()`. ([Accessing files from the macOS App Sandbox](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox))

Keep one stable bundle ID and signing identity. macOS uses code-signing requirements to track access to protected resources, and Service Management also links helpers and login items to their app and signing team. Changing identity can make macOS treat a later build as a different app and ask again. ([Creating distribution-signed code for macOS](https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac), [Service Management update guide](https://developer.apple.com/documentation/servicemanagement/updating-helper-executables-from-earlier-versions-of-macos))

## Menu bar and login lifecycle

SwiftUI's `MenuBarExtra` is enough for a menu-only app and can use a window-style panel for richer status. Set `LSUIElement` to hide the Dock and app-switcher icon. Apple notes that macOS terminates a menu-only app if the user removes its menu extra, so Caddie must restore its full status from durable Caddie state when the user starts it again. ([`MenuBarExtra`](https://developer.apple.com/documentation/swiftui/menubarextra), [`LSUIElement`](https://developer.apple.com/library/archive/documentation/General/Reference/InfoPlistKeyReference/Articles/LaunchServicesKeys.html))

On macOS 13 and later, register the main app with `SMAppService.mainApp.register()`. A main-app service launches on later logins. Registration remains subject to user approval, and `status` can become `requiresApproval` if the user revokes consent. Show that state in Caddie and offer `openSystemSettingsLoginItems()`; do not try to bypass it. This use does not need a separate login helper because the menu app itself performs the work. ([`SMAppService`](https://developer.apple.com/documentation/servicemanagement/smappservice), [`register()`](https://developer.apple.com/documentation/servicemanagement/smappservice/register%28%29), [`requiresApproval`](https://developer.apple.com/documentation/servicemanagement/smappservice/status-swift.enum/requiresapproval), [Service Management update guide](https://developer.apple.com/documentation/servicemanagement/updating-helper-executables-from-earlier-versions-of-macos))

## Notifications and attention

Use User Notifications only for Caddie items that need attention. Ask for alert and sound permission in context, such as after the user turns on notifications or after the app can show what it would report. The first explicit request prompts once; later calls do not prompt again. Check `notificationSettings()` before each send because the user may change settings at any time. A denied notification must not hide the same item from the menu and durable Caddie attention state. ([Asking permission to use notifications](https://developer.apple.com/documentation/usernotifications/asking-permission-to-use-notifications), [`UNNotificationSettings`](https://developer.apple.com/documentation/usernotifications/unnotificationsettings), [`getNotificationSettings`](https://developer.apple.com/documentation/usernotifications/unusernotificationcenter/getnotificationsettings%28completionhandler%3A%29))

## Signing, notarization, and personal use

Apple lets a developer build and test a macOS app with Xcode and a free Apple Account. Xcode also offers “Copy App,” which produces an unsigned Mac app. That is enough for a local trial, but use a stable development signature for real login-item and privacy tests. Apple reserves Developer ID and notarization for Apple Developer Program members. ([Choosing a Membership](https://developer.apple.com/support/compare-memberships/), [Xcode distribution methods](https://developer.apple.com/documentation/xcode/distributing-your-app-for-beta-testing-and-releases))

If the app leaves the development Mac—even for direct personal sharing—sign the app and every nested executable with Developer ID, enable Hardened Runtime, add a secure timestamp, submit it to Apple's notary service, and staple the ticket to the shipped app or disk image. App Sandbox remains optional for direct distribution. The Mac App Store is out of scope for the first release because it requires App Sandbox and would force a new Tool execution and file-access design. ([Developer ID certificates](https://developer.apple.com/help/account/certificates/create-developer-id-certificates/), [Notarizing macOS software](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution), [Hardened Runtime](https://developer.apple.com/documentation/xcode/configuring-the-hardened-runtime), [Packaging Mac software](https://developer.apple.com/documentation/xcode/packaging-mac-software-for-distribution))

## Constraints for later decisions

- The first release should require macOS 13 or later so one code path can use both `MenuBarExtra` and `SMAppService`.
- The app should run a full Caddie inspection at launch and after any uncertain File System Events signal. It should never derive a managed-state change from a file event alone.
- The app should use the existing User Caddie State Root for sync and attention records. App preferences may hold UI choices, but they must not become another account of skill state.
- The first release should stay outside App Sandbox. Moving to the Mac App Store would be a new effort with a bundled Tool/runtime and security-scoped access design.
- The App–Tool contract still needs a decision on Tool discovery, Node discovery or bundling, version checks, cancellation, time limits, and JSON error handling.
- Routine sync can run in the main login app. Add a launch agent or daemon only if a later requirement says work must continue after the user quits or removes the menu app.
